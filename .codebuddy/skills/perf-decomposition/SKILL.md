# 性能分解测量

## 概述

**对 JS/TS 性能的直觉不可靠 —— 包括「这个优化省不了多少」这种保守判断。**

实测经验（一个会话内连续 5 次）：把功劳归给算法（实际 88% 来自消灭 per-item 分配）、
把收益归给对象分配（实际不成立）、以为模糊匹配是瓶颈（实际不是）、以为单趟双累加器
省不了多少（实际 1.86x）、以为 int8 能省内存带宽（实际 1.05x，因为循环是算力受限）。

**高估和低估都会发生，所以规律不是「我偏乐观」或「我偏悲观」，而是「直觉本身不可用」。**

## 铁律

```
没有分解实验，不许说「因为 X 所以快」
没有独立参照，不许说「行为等价」
没有验证过测试会失败，不许说「这是回归测试」
```

## 步骤

### 1. 先建可复现的分解基准

参照本仓库的 `scripts/bench-search-perf.mjs`：**每个实验只变一个变量**，
把「改前 vs 改后」拆成多档中间态，从而分离出各项贡献。

```
V0 旧实现 → V1 只去掉分配 → V2 再换算法 → V3 含输出成本
         ↑ 分配的成本      ↑ 算法的成本    ↑ 新增的代价
```

只做「改前/改后」对比只能得到倍数，得不到原因，也无法判断哪一项才是大头。

### 2. 计时方法

- **预热**：正式计时前先跑几次，触发 JIT 优化。
- **取多批次最小值，不要取均值**。噪声（GC、JIT 抖动、调度）只会让某次变慢、
  不会让它变快，所以 min 最接近真实成本。均值会被 GC 尖峰污染，导致不同写法之间
  的比较**不可复现**（实测中同一对写法两次跑出互相矛盾的结论）。
- 语料要贴近真实分布（长度、词频、维度），否则结论会失真。
- 异步/延迟场景看**比值**而非绝对值（`setTimeout` 有最小粒度，会放大绝对值）。

### 3. 等价性验证

- **参考实现必须独立于被测代码**。若两边共用同一批底层原语，原语里的公式错误会让
  两边一起错、对拍照样通过。至少补一条**手算基准**：构造能精确推导期望值的输入，
  期望值来自公式而非运行代码。
- 断言强度要匹配声明：声称「逐位一致」就用 `toBe`，不要用 `toBeCloseTo` 掩盖差异。
- 注意**代数退化**：某些参数在特定语料下会约掉（如等长文档使长度归一化失效），
  此时测试钉不住它们 —— 换一组语料覆盖。

### 4. 回归测试必须先验证它会失败

写完回归测试后，**临时把 bug 改回去跑一次**，确认测试确实红了，再恢复。
否则你无法区分「测试有效」和「测试根本没覆盖到那条路径」。

同一原则用于时序/阈值类测试：先算清时钟消耗了几次 tick（`measure` 消耗两次
`now()`，但阶段耗时只等于**一个增量**），否则阈值断言会算错。

### 5. 注释里的数字

- 写**区间**（如「约 1.7~1.9x」）而非精确值，并注明**可复现的脚本 + 实验号**。
- 注释里的断言（「XX 时调用」「永远可用」「不可能发生」）最容易被后续重构悄悄证伪。
  错注释比代码 bug 更危险：代码 bug 会报错，错注释只会误导人做决定。
  **重构时把「改注释」当成改动的一部分，而不是可选的美化。**

## 常见陷阱（实测过的）

| 现象 | 真实原因 |
|---|---|
| 热循环里慢 | 往往是 **per-item 对象分配**（`new Map()`/`new Array().fill()`/`{...}`），不是算法 |
| 闭包慢 | 是**被捕获的变量**退化为堆上 context 访问，不是函数调用开销（后者可忽略） |
| 改成 int8/小类型没变快 | 循环是**算力受限**而非内存带宽受限；JS 不自动向量化 |
| 排序改部分选择收益小 | 点积/扫描等**固定成本**占大头，选择阶段只是零头 |
| 并行没提速 | 该路径是 **CPU 受限**；只有延迟受限（等 I/O）时并发才有收益 |
| 微基准结论不可复现 | 用了均值而非 min；或预热不足 |

## 何时**不该**继续优化

- 剩余成本已进入递减区（如总耗时已到个位数 ms、大头是外部 I/O）。
- 优化要引入复杂度/精度风险，而收益只有几个百分点 —— 此时**正确性、可观测性、
  可测试性**的收益更高。
- 判断依据是分解数据，不是「感觉还能再压」。

## 与其它技能配合

- 改完 → `verification-before-completion` 跑全套验证（单测 + 类型 + lint + e2e + 构建）。
- 大改动 → `requesting-code-review` 派独立审查。**自己的代码自己审不出来**：
  你会因为「知道自己是这么写的」而默认它没问题。审查员没有先验，只看结构。
- 审查意见 → `receiving-code-review`，逐条用技术理由回应，不敷衍附和也不盲目执行。
